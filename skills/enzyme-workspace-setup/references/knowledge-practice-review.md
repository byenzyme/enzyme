# Knowledge Practice Review Contract

This reference defines the product-neutral judgment used during knowledge-workspace
setup. The product adapter that includes it still owns every command, schema,
permission boundary, mutation rule, recovery promise, and verification step. This
reference grants no authority to write or reorganize anything.

## Read evidence as evidence

Read the complete bounded evidence supplied by the product before forming a view.
Treat rankings, candidates, counts, metadata, and samples as clues rather than a
diagnosis. A prominent folder can be incidental; a small linked or dated series can
hold the real continuity. Use representative source content and patterns of use,
not folder names alone, to decide what something means.

Distinguish findings from hypotheses. A finding is directly supported by the
available evidence. A hypothesis is a plausible interpretation that still needs a
sample, a product-supported proof, or the user's correction. Preserve disagreement
and absence in the evidence instead of forcing a recommendation.

## Form a recognizable account

Describe the practice in the user's vocabulary before discussing settings. A useful
account says:

- what the practice appears to be and where its history accumulates;
- which projects, subjects, decisions, or relationships continue over time;
- which material looks incidental, generated, or merely structural; and
- one or two consequential questions the material may now help answer.

Name recognizable sources and connections, but translate implementation details
into what they mean for the user's work. Ask for a plain-language correction to
this account when the product workflow provides a recognition pause. Do not turn
that pause into a taxonomy, profile, continuity, or attention questionnaire.

A healthy practice may need no setting change. That is a successful outcome, not a
missing recommendation: explain what is already coherent, prove it with real source
material, and leave the structure alone.

## Prefer meaningful continuity over structural noise

Recommend a durable handle only when it names continuity already present in the
material. Folders, dates, tags, links, stable names, and running logs can all be
handles, but none is valuable merely because it exists. Tidiness, frequency, or a
plausible label does not establish importance.

Do not invent a new information architecture, infer identity from a folder name, or
turn every candidate into configuration. When evidence is uncertain, prefer the
product's adaptive/default behavior and keep the uncertainty visible.

## Help the user keep hold of one important thread

Sometimes the material shows something the user cares about — a project they want
to finish, a relationship they want to tend, a question they keep returning to —
but the trail fades between notes. Start with what they risk losing, not with
missing metadata.

Offer one small habit for new notes when it would keep that trail alive. Offer a
second only when it serves a clearly different part of the user's life or work.
Phrase each one in ordinary language:

> When you <something you already do>, add <one small, familiar cue>, so later you
> can ask <a question worth being able to answer>.

Use a moment that already happens and a cue the user already understands: the same
name, link, tag, date style, folder, or running note. Show exactly what this would
look like in their next note. Make clear that old notes do not need to be cleaned
up first. Do not say “tag more,” “be consistent,” or “start daily notes” without
connecting the suggestion to something the user wants to remember or revisit.

If the product can remove a step by changing a template or other aid the user
already uses, offer that help after explaining the value and ask before changing
it. Do not introduce a new system merely to enforce the habit.

Later, when the user has naturally made enough new material, test the promise. Show
whether the thread can now be recovered and whether the question can be answered.
If it cannot, revise or drop the suggestion; do not treat that as the user's
failure.

## End insight-first

Lead the final handoff with what the proof revealed, not with setup machinery.
Answer one question about the recognized practice in two to four plain-language
sentences grounded in returned source excerpts. Cite the supporting material and
name the useful pattern, change, tension, or connection. If the evidence cannot
support an honest insight, say so and offer a narrower next question.

Then state what the setup now makes possible and give one natural next question.
Do not mistake a successful command, a result count, or a nearby semantic match
for proof of the user's actual question.

## Choose what can keep returning

Choose the continuation from the practice the evidence actually shows.

When the user already writes on a real daily or weekly rhythm, first produce a
short, cited look-back from those notes. Return one goal, commitment, recurring
concern, or sign of movement. The review itself is the proof; scheduling is only
a way for that value to return. If the product can create recurring tasks, offer
one simple cadence only after showing the review. Create nothing without a clear
yes to the review, cadence, and destination. Each run should cite its sources,
say when there is not enough evidence, and stay out of the source material unless
the user separately permits writing there. If the product cannot schedule the
review, leave the user with a reusable question instead of implying it was
scheduled.

When the user does not write on a schedule, do not prescribe daily notes or
automation. If an important trail is easy to lose, use the small-habit guidance
above and show the next-note example. Otherwise leave the practice alone and
continue with the strongest question the existing material can answer now.

Put the operational receipt last: boundaries, settings in the user's language,
successful preparation or refresh steps, consequential limitations, and how to
undo any accepted change. The user should leave with a felt use for the product,
not a lesson about its machinery.
